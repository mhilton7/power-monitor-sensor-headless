# PZEM driver

`pm_meter_driver_t` is a versioned interface. The physical implementation is explicitly named `pzem-004t-v4-classic-candidate`; no generic V3 library or Arduino runtime is present. RC8 permits this selected driver to poll in a non-production validation mode while physical certification remains pending. Production compilation still fails unless a variant and marked-unit evidence are selected.

Candidate transaction: UART1 GPIO17/18, 9600 8N1, slave 1. The eight-byte request is `01 04 00 00 00 0A` plus little-endian Modbus CRC16. The response must be exactly 25 bytes, matching slave/function and CRC. It decodes voltage (0.1 V), current (32-bit low/high, 0.001 A), active power (32-bit low/high, 0.1 W), cumulative energy (32-bit low/high, Wh), frequency (0.1 Hz), and power factor (0.01). Frames are rejected for timeout, short length, CRC, wrong slave/function, or bounded range failure.

The one-second sampler retains UTC trust and monotonic time and offers each validated reading to the fixed one-in-flight/one-newest-pending telemetry slot. Firmware reports the PZEM cumulative watt-hour counter as measured; it does not aggregate intervals, integrate a fallback energy history, or persist measurements. The central server owns interval aggregation and compares accepted cumulative counters for gap-energy recovery, reset/rollover handling, and plausibility without inventing a power curve. Current warnings occur at 80%/90% of the configured CT rating. Routine reboot and OTA never issue a PZEM counter-reset operation; the active image has no sensor-side data-reset or SD-format command.

The RC validation and certified-production modes execute the identical driver path; only their admission evidence differs. Exact delivered-unit markings, electrical levels, and counter behavior remain pending per `HARDWARE_IDENTITY.md`.
