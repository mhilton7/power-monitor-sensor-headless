# Release process

1. Work on `codex/release-0.1.0-rc.23`; review status and ensure generated/secrets files are untracked.
2. Run host/pure-C tests, PowerShell AST parse, secret/source policy, the live OSV audit, and the digest-pinned ESP-IDF release-candidate build.
3. Assemble artifacts with `tools/Build-Release.ps1`; it refuses a dirty tree, enables ESP-IDF reproducible-build mode, injects a strictly validated release SemVer into `esp_app_desc_t`, requires the compiled app version to match the requested version, records the exact embedded ELF SHA-256 as `firmware_build_id`, validates `manifest.json` against `release/manifest.schema.json`, consumes a fresh passing OSV report, and emits a complete ESP-IDF component-graph SPDX SBOM. Independently verify `SHA256SUMS`, `compatibility.json`, provenance/reports, and flash offsets.
4. For this RC, include `hardware-certification-status.json` with `pending`; name the tag `v0.1.0-rc.23` and mark the GitHub Release prerelease.
5. Publish firmware `v0.1.0-rc.23` build 26 only with coordinated PowerMeter V2 server `v0.1.0-rc.23`. The manifest and compatibility asset must name that server tag, declare `contracts.telemetry_protocol` as `pm-telemetry/2.0.0`, and bind the final generated server OpenAPI SHA-256 recorded in `test/vectors/server-contract.json`. RC23 retains the byte-identical RC22 runtime sources, partition layout, sdkconfig profiles, and dependency locks while preserving identity, configuration, secure OTA, and `pm-protocol/1.0.0`. Firmware RC22 remains immutable public evidence, and server RC22 remains immutable failed-candidate evidence after its deployment smoke blocked publication. Do not move, delete, or republish RC22 or any earlier public firmware tag.
6. Stable promotion is prohibited until detached `hardware-certification.json` passes the schema/semantic gate for the exact source commit and production-profile binary. The signed `hardware-certification-<commit>` tag annotation anchors the evidence SHA without a self-referential source commit. Stable configuration also requires NVS encryption/eFuse key provisioning according to the secured manufacturing procedure.

Stable evidence is never committed. Publish it first as the sole
`hardware-certification.json` asset of a separate, non-draft GitHub Release whose signed
annotated tag is `hardware-certification-<40-character-source-commit>` and targets that exact
commit. The signed tag annotation must contain exactly one line of this form:

```text
hardware-certification-sha256: <lowercase SHA-256 of hardware-certification.json>
```

Only then push the stable `vX.Y.Z` tag. The workflow downloads the detached asset into ignored
`test-results/release-input/` and rejects an unsigned/lightweight tag, a wrong target commit, a
missing/draft/duplicate asset, a digest mismatch, invalid marked-unit evidence, or a rebuilt
firmware hash that differs from the certified image.

Local RC commands:

```powershell
. C:\Espressif\tools\Microsoft.v6.0.2.PowerShell_profile.ps1
.\tools\Build-Release.ps1 -Version 0.1.0-rc.23 -BuildNumber 26
Get-Content .\release\out\0.1.0-rc.23\SHA256SUMS
git tag -s v0.1.0-rc.23 -m 'PowerMeter sensor 0.1.0-rc.23'
git push origin codex/release-0.1.0-rc.23
git push origin v0.1.0-rc.23
```

The final two pushes are publication actions and are executed only by the release owner after review. An unsigned or lightweight tag is rejected; if a configured signing key is unavailable, publication remains blocked. The tag workflow repeats all release/security gates from a clean checkout, uploads flashable artifacts, and creates the prerelease. Per-device OTA nonce/signature is generated by the compatible server at rollout; it is never committed.
