# Release process

1. Work on `codex/release-0.1.0-rc.5`; review status and ensure generated/secrets files are untracked.
2. Run host/pure-C tests, PowerShell AST parse, secret/source policy, the live OSV audit, and the digest-pinned ESP-IDF release-candidate build.
3. Assemble artifacts with `tools/Build-Release.ps1`; it refuses a dirty tree, enables ESP-IDF reproducible-build mode, injects a strictly validated release SemVer into `esp_app_desc_t`, requires the compiled app version to match the requested version, validates `manifest.json` against `release/manifest.schema.json`, consumes a fresh passing OSV report, and emits a complete ESP-IDF component-graph SPDX SBOM. Independently verify `SHA256SUMS`, `compatibility.json`, provenance/reports, and flash offsets.
4. For this RC, include `hardware-certification-status.json` with `pending`; name the tag `v0.1.0-rc.5` and mark the GitHub Release prerelease.
5. Publish firmware `v0.1.0-rc.5` before server `v0.1.0-rc.5`. The server must fetch and validate the exact firmware compatibility/manifest asset and SHA, then run `gh attestation verify firmware.bin --repo mhilton7/power-monitor-sensor-headless`; it must not trust a floating branch. RC5 changes only release identity and the full-byte OpenAPI traceability binding for the audited server RC5 contract; do not move, delete, or republish any prior tag. Public firmware RC4 remains immutable. Its matching server RC4 passed compatibility, mandatory test/security/migration gates, all four image publications and attestations/scans, and anonymous GHCR access, but its digest-pinned deployment smoke deterministically restarted the completed one-shot initializer during runtime-only recovery. The unchanged initializer `FinishedAt` assertion therefore failed, release assembly was skipped, and no server RC4 GitHub Release or install bundle was published; preserve it only as non-installable historical prepublication evidence.
6. Stable promotion is prohibited until detached `hardware-certification.json` passes the schema/semantic gate for the exact source commit and production-profile binary. The signed `hardware-certification-<commit>` tag annotation anchors the evidence SHA without a self-referential source commit. Stable configuration also requires NVS encryption/eFuse key provisioning according to the secured manufacturing procedure.

Stable evidence is never committed. Publish it first as the sole
`hardware-certification.json` asset of a separate, non-draft GitHub Release whose signed
annotated tag is `hardware-certification-<40-character-source-commit>` and targets that exact
commit. The signed tag annotation must contain exactly one line of this form:

```text
hardware-certification-sha256: <lowercase SHA-256 of hardware-certification.json>
```

Only then push the stable `vX.Y.Z` tag. The workflow downloads the detached asset into ignored
`test-results/release-input/` and rejects an unsigned/lightweight tag, a wrong target commit, a
missing/draft/duplicate asset, a digest mismatch, invalid marked-unit evidence, or a rebuilt
firmware hash that differs from the certified image.

Local RC commands:

```powershell
. C:\Espressif\tools\Microsoft.v6.0.2.PowerShell_profile.ps1
.\tools\Build-Release.ps1 -Version 0.1.0-rc.5 -BuildNumber 1
Get-Content .\release\out\0.1.0-rc.5\SHA256SUMS
git tag -s v0.1.0-rc.5 -m 'PowerMeter sensor 0.1.0-rc.5'
git push origin codex/release-0.1.0-rc.5
git push origin v0.1.0-rc.5
```

The final two pushes are publication actions and are executed only by the release owner after review. An unsigned or lightweight tag is rejected; if a configured signing key is unavailable, publication remains blocked. The tag workflow repeats all release/security gates from a clean checkout, uploads flashable artifacts, and creates the prerelease. Per-device OTA nonce/signature is generated by the compatible server at rollout; it is never committed.
