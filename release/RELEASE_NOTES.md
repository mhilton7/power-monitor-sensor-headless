# PowerMeter Sensor Headless 0.1.0-rc.15

RC15 repairs two backlog failure modes observed on RC14 while preserving all stored measurements, configuration, device identity, sampling cadence, and `pm-protocol/1.0.0`. Before transmission, firmware now measures the complete serialized reading batch and deterministically selects the largest prefix whose JSON body fits the authenticated 8,192-byte transport limit. Records excluded from that request remain on microSD and are retried in sequence; acknowledgement advances only after an authenticated server response. A fresh, storage-task-owned inventory across every active, rotated, and quarantined journal file can now prove a missing prefix between the server acknowledgement and the oldest locally retained sequence, report that exact bounded range through the existing authenticated permanent-loss endpoint, and resume backlog delivery only after the server accepts it. Unmounted, incomplete, unreadable, or structurally ambiguous inventories fail closed; a corrupt span is reportable only when scanning resynchronizes at a later valid record and therefore bounds the exact missing range. No storage formatting, NVS erase, identity reset, reprovisioning, server change, or protocol change is introduced. RC15 remains compatible with public PowerMeter V2 server `v0.1.0-rc.14`; public RC14 remains immutable.

RC8 carries forward RC6's repair for the pre-provision boot crash present in public RC1-RC5 firmware. An actual RC1 device exposed two roughly 18 KiB command-ledger objects on the 3,584-byte ESP main-task stack, corrupting execution before USB provisioning could start. RC6 removed that oversized frame, moved other bounded workspaces to zeroized PSRAM-first allocation, increased deliberately sized task stacks, and enforced a 3,072-byte maximum first-party function frame in both compilation and independent object inspection.

Its exact enrollment, heartbeat, reading-batch, permanent-loss, OTA-download, destructive-command, credential-rotation, HKDF, and base64 HMAC contracts are locked by cross-repository vectors and coordinated with PowerMeter V2 server `v0.1.0-rc.14`. The complete generated server RC14 OpenAPI document is bound by SHA-256 `26dbc5cf443cb63a29ca1f22bc069b566afa4eb026ed5c86023a81ffd299d1fe`. Firmware also authenticates server response bytes, timestamps, and nonces before applying acknowledgements or commands. The shared protocol remains `pm-protocol/1.0.0`.

Configuration and command A/B recovery now distinguish missing records from corruption or I/O failure, serialize writers, bind staged content at commit, reject ambiguous equal generations and generation exhaustion, and reconcile interrupted commands by an explicit boot policy. Outbound HTTP and OTA operations capture one immutable origin/CA/device/key tuple so credential rotation cannot tear an in-flight request. Required runtime tasks start behind a common gate and roll back as a set on allocation failure.

Sequence, device-identity, and OTA-checkpoint persistence now creates state only when its NVS records are truly absent, fails closed on corruption or I/O errors, rejects ambiguous equal generations and generation exhaustion, and verifies every critical OTA checkpoint write. OTA installation is single-flight, and transient Wi-Fi configuration copies are explicitly zeroized.

USB provisioning and physically authorized recovery now run in an isolated maintenance boot without measurement, normal networking, commands, or OTA producers. Candidate state is cleared on every failed boundary, oversized serial lines are discarded through newline, and safe reboot occurs only after its durability barrier and complete serial transmission. PowerShell tooling accepts a canonical trailing slash on the HTTPS origin, validates the local CA before opening COM, distinguishes real serial deadlines from Windows semaphore failures, and never rolls back after a commit request may have reached the device.

Public firmware/server RC6 remain immutable and installable. RC8 is a coordinated firmware/server release candidate: publish the signed firmware prerelease first, then set the server compatibility gate to the same RC8 tag before publishing the server images and deployment YAML. RC7 was a local, unpublished validation candidate: its first live OTA attempt proved that firmware used ESP-IDF's request-header accessor when authenticating server response headers. The server consequently recorded the command as delivered while the sensor rejected the heartbeat before parsing it. The same defect existed in the OTA download path. RC8 captures only the required response headers through bounded ESP-IDF response-header events, rejects missing, duplicate, or oversized values, and adds regression coverage for both heartbeat and OTA paths. Because affected firmware cannot receive this fix through OTA, one NVS-preserving USB flash is required before future OTA use.

Credential rotation stages the server-generated candidate in an inactive CRC/read-back-verified config slot, commits under the old directional key, reports activation under the new key, and retains a byte-stable result until authenticated acknowledgement. The A/B rotation and destructive-operation journals resume after power loss at each durable boundary; secret-bearing temporary buffers and consumed tokens are explicitly zeroized.

RC8 retains RC7's separation of live candidate polling from physical certification. Its release-candidate profile enables the real, read-only PZEM UART driver while keeping `CONFIG_PM_HARDWARE_IDENTITY_VERIFIED=n`, `hardware_certification: pending`, and the production gate closed. The one-second sampling cadence, UART1 GPIO17/18 at 9600 8N1, 350 ms bounded read, task priorities/stacks, queue sizes, 60-second durable interval, and 15-second heartbeat are unchanged. `meter_self_test` reads the latest locked sample and cannot create a second UART transaction. Stable production promotion remains blocked until the exact marked unit, TTL electrical behavior, register map, OTA rollback, and 72-hour soak pass the machine-readable hardware certification gate. Simulation remains excluded from real evidence.

All energy, interval, completeness, and uploaded history evidence originates only from validated PZEM frames. Utility-bill content is outside this firmware and cannot enter its measurement or storage path.
